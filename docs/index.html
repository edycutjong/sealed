Exhibit procedure · five parts, one flow

Run it, don't read it.

No triager decides. The rules are written before any bug exists; a TEE runs the exploit against them; the contract pays or refuses.

Executed, not judged

The pinned verifier replays the exploit in revm on the committed snapshot and asks the level's own validateInstance: the Ethernaut level's rule, not ours.

Seal, then commit

The hunter stores the exploit as an OutLayer encrypted secret, then commits H(exploit ‖ hunter ‖ salt) with a bond.

0access keys on the bounty

Nobody holds the key

The demo and corpus bounties were created from one global contract hash with no access keys. Nobody can pull awarded escrow.

NEAR global contract · 7HtmeswB…

Refused, with a reason

Six refusal kinds, each fired on chain. A refused verdict or an expired award slashes the bond; the other refusals only log the reason.

  • delivery mismatch
  • invariant busy
  • pool pull
  • duplicate
  • expired award
  • fake

Delivered, hash-checked

The exploit goes to the protocol sealed to its key. The contract pays only if sha256(enc) equals the hash the worker attested.

crypto_box · I8 delivery hash

Honest by design

What this does not prove yet.

  1. Testnet only. The mainnet leg is prepared (scripts/mainnet_leg.py) and has not run.
    README · Honest limits, item 1
  2. Worker attestation. make verify shows the request pinned the verifier hash and the operator's OutLayer worker key answered (a FunctionCall key limited to OutLayer's contract, its method list including resolve_execution). It checks the key, not its TDX quote, and does not show the worker ran exactly those bytes. make replay re-runs the same bytes locally.
    README · Honest limits, item 2
  3. No outside users yet. The measured demo is our own hunter agent plus the fakes corpus.

Questions from the bench

Questions a judge would ask.

Each answer points at a file or a command in the repo.

Do I need a NEAR account to check any of this?

No. make replay re-runs every published verdict offline with the verifier wasm each bounty pinned; make verify reads chain data from a public archival RPC (make verify-demo: the five paid runs, about 1.5 min).

What does the TEE prove, exactly?

That the request pinned the verifier hash and a registered OutLayer worker key answered, not that the worker ran exactly those bytes. make replay runs the same bytes on your machine.

What stops junk submissions?

A bond on every commit, slashed on a refused verdict, and the level's own check: 21 fakes on chain, 0 paid. The heaviest abuse input used 23.98% of the 2e9-instruction limit.

What stops the protocol from walking away?

The bounties have no access keys and their rules are fixed at funding. Reserved and awarded escrow cannot be withdrawn (I4); only the unreserved pool can, after a timelock (7 days by default).

What is mocked?

The 20 sandbox tests use a mock OutLayer and token. The 29 testnet runs use the live OutLayer worker and a test token; mainnet has not run.

Why not let an LLM triage the reports?

On the same 21 fakes, LLM-only triage paid 1, 3 and 3 (third-party models, one run each, not NEAR AI Cloud). The executing verifier paid 0. See baseline/README.md.

Re-check it yourself.

Replay offline, then check the payouts from chain data. No NEAR account, no keys.

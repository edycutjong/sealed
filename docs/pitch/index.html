How a bounty runs.

SEALED · the path · ARCHITECTURE.md “Commit to payout” · contracts/bounty/src/lib.rs · scripts/hunter.py · corpus/refusals.json
Ten steps, three phases. The hunter stores the exploit as an OutLayer encrypted secret first; the bounty contract never sees it. Then it commits the hash with a bond. The bounty asks OutLayer to run the verifier pinned by hash; a TEE worker reads the secret and replays the exploit on the committed snapshot. OutLayer's resolve_execution hands the verdict to the bounty's on_verdict, which awards escrow once per invariant. Delivery must hash to h_enc before ft_transfer pays. Every refusal is a successful transaction with a reason; six kinds, all seen on testnet.

Where trust bottoms out.

Two tiers you can re-run yourself. One you take on trust.

Checked from chain

make verify
  • The request pinned the verifier hash.
  • The operator’s scoped worker key answered.
  • verify-demo: the bounty has 0 access keys.

Re-run offline

make replay
  • The same pinned bytes under wasmtime reproduce all 29 on‑chain verdicts.
  • From a fresh clone: no NEAR account, no keys.
  • No network, no Rust.

not checked
